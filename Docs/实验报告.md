## 1 游戏概念设计（团队公共部分）

### 1.1 游戏概念

**Campus Night Market（校园夜市）** 是一款以校园夜市经营为主题的**2D俯瞰视角**、**单人回合制模拟经营游戏**。玩家扮演背负贷款的研究生，在华科校园及周边地图中通过白天走格收集资源、购买地块、建设夜市，并在夜晚进行客流结算，最终在限定天数内达成还款目标。

### 1.2 游戏简述

游戏以华中科技大学校园为背景，构建了"白天积累、夜晚收获"的日循环体系。

**白天阶段**：玩家投掷1-6点骰子，在校园地图上移动。到达不同地块触发相应交互——资源点采集食材、可建地块购买地皮建设夜市、已有夜市中增设和升级摊位、事件地块遭遇随机事件。体力作为瓶颈资源限制每日步数。

**夜晚阶段**：系统自动遍历所有营业中夜市，综合考虑摊位吸引力权重、客群偏好、食材库存、天气倍率、卫生状况以及夜市等级效果，按多层系数计算总收入。

**经营风险**同样丰富：卫生审查系统随机抽查夜市，不合格导致停业罚款；随机事件系统在多个时机带来收益或损失；贷款利息每7天结算，资金不足时自动滚入本金形成复利压力。

游戏核心理念是"扩张经营"与"风险控制"的策略权衡——积极扩张提升收入上限，但带来更高管理成本和风险敞口。

**单日游戏流程：**

```
  DayStart（天气刷新+每日事件）
      ↓
  RollDice（投骰1-6点）
      ↓
  ChooseMove（选择可达目标）
      ↓
  MovePlayer（沿路径移动，消耗体力）
      ↓
  TileInteraction（地块交互）
      ↓
  NightSettlement（事件→天气→结算→卫生检查）
      ↓
  DayEnd（利息处理→胜负判定→进入下一天）
```

## 2 游戏总体设计（团队公共部分）

### 2.1 总体方案设计

采用**Unity 2020.3.30f1c1**引擎，C#语言，目标平台Windows。架构为**面向对象的分层模块化设计**。

**系统架构：**

```
┌────────────────────────────────────────────────────────────┐
│                    UI表现层（S01/S02场景）                   │
│  主菜单 · HUD · 地块交互面板 · 夜市面板 · 消息栏 · 弹窗     │
├────────────────────────────────────────────────────────────┤
│                      系统管理层（10个管理器）                  │
│  GameManager(全局状态)→TurnManager(阶段流)→MapManager(地图) │
│  →TileManager(地块交互)→MarketManager(夜市)→EconomyManager │
│  (经济结算)→ResourceManager(资源)→CustomerManager(客流)     │
│  →EventManager(事件)→WeatherManager(天气)→InspectionManager │
│  (卫生检查)→PrototypeBootstrap(测试总入口)                  │
├────────────────────────────────────────────────────────────┤
│                   数据配置层（ScriptableObject）             │
│  MapConfig / TileConfig / StallConfig / GameEvent / 天气预设 │
└────────────────────────────────────────────────────────────┘
```
图2-1 系统整体架构图

**设计原则：**
1. **配置驱动**：所有数据使用ScriptableObject资产，数据与逻辑分离
2. **职责单一**：每个管理器只负责自己领域，跨系统通过公开方法+事件通信
3. **三段式事务**：资源操作"检查→扣费→执行→回滚"
4. **事件驱动**：阶段切换、天气变化、骰子投掷通过C#事件通知UI

**白天数据流转：**
```
TurnManager.RollDice → MapManager.GetReachableTiles（BFS） → 
玩家选择 → ResourceManager.ConsumeEnergy → 
MapManager.TryGetPath（路径） → PlayerMover.MoveAlongPath → 
TileManager.BeginTileInteraction → EventManager触发到达事件 → 
地块交互完成 → 准备下一次投骰或进入夜晚
```

**夜晚数据流转：**
```
TurnManager.NightSettlement → EventManager触发夜晚事件 → 
WeatherManager获取倍率 → EconomyManager.SettleAllMarketsNightIncome → 
  CustomerManager按吸引力分配客流 → 偏好加权 → 食材判定 → 
  天气×卫生×等级加成 → AddMoney → 
InspectionManager.ExecuteNightlyInspections → 
MarketManager.AdvanceClosedRounds → 
EconomyManager.ProcessLoanInterest → 
GameManager.EvaluateGameResult
```

### 2.2 关键技术

**1. 广度优先搜索路径算法**
地图系统使用BFS从当前位置沿TileConfig.nextTileIds邻接表扩展，返回所有步数≤骰子点数且≤体力的目标地块及完整路径。visited集合防止环路死循环，等长路径按配置顺序取第一条保证结果稳定。

**2. ScriptableObject配置驱动**
六种地块类型（Start/Buildable/Resource/Shop/Event/Special）按7大字段分组：标识、地图、经营、客流、风险、交互。所有数据通过资产文件加载，数值策划可直接调整配置。

**3. 多层系数收入结算**
```
总收入 = 基础客流 × 竞争削减 × 等级加成(×1.2) × 吸引力权重分配 
         × 客群偏好加权 × 食材惩罚(不足×0.5) × 天气倍率(×0.4~×1.1) 
         × 卫生加成(×0.95~×1.1) × 4级夜市加成(1+reputation×0.01)
```

**4. 事件策略模式**
EventEffectType分发到对应管理器执行。二选一事件通过requireChoice标记挂起，等待UI回调MakeEventChoice()应用选择效果。

**5. 事务封装**
所有资金操作封装为"CanXxx检查→SpendMoney扣费→执行→失败AddMoney回滚"。

**6. 原型总控集成**
PrototypeBootstrap作为测试入口，统一初始化10个系统管理器、绑定引用关系、串联投骰→移动→交互→结算的完整流程，每帧通过OnGUI调试面板实时显示所有系统状态。

## 3 整体架构与夜市/摊位系统实现（高致远）

### 3.1 子任务描述

作为系统策划和主程，我的任务是"搭骨架"：设计全套基础枚举和数据结构让各模块有统一的"语言"；实现GameManager管生命周期和胜负判定，TurnManager管每天从起床到打烊的完整流程；实现MarketManager提供夜市经营全部基础功能，并预留清晰的跨系统接口。同时负责制定团队命名规范，确保5人写的代码风格一致。

### 3.2 子任务设计

**GameManager——轻量化状态机**

我把它设计得尽量轻量：不包含地图、经济、移动逻辑，只维护全局阶段和胜负判定。胜负判定放在AdvanceDay中——只有限期日当晚判定一次，避免结算多次调用时出错。胜利后进入无尽模式、贷款清零，让玩得顺手的玩家继续经营。

**TurnManager——水管式阶段流**

把游戏拆成10个清晰的GamePhase阶段，TurnManager只负责按顺序推进，不关心每个阶段里发生了什么。UI监听PhaseChanged事件即知该显示什么。投骰、选目标、移动完成、交互完成、结算完成——每个步骤都有明确的Notify方法。

**MarketManager——预留接口设计**

夜市经营涉及几乎所有其他系统，我先把纯夜市逻辑写完整（创建/升级/摊位建设/升级/停业管理/汇总刷新），在每个需要外部介入处用注释标记"这里需要xxx接入"。

**基础枚举与数据结构：**

**夜市升级规则：**
```
等级1→2：费用2000，最大摊位2，效果"客流承载+20%"
等级2→3：费用5000，最大摊位3，效果"解锁高端摊位"
等级3→4：费用10000，最大摊位4，效果"口碑加成(1+reputation×0.01)"
```
摊位升级系数1+(level-1)×0.1，线性增长确保后期边际收益递减。

**胜负判定逻辑：**
```csharp
public void EvaluateGameResult(PlayerRuntimeData playerData, MapConfig mapConfig) {
    if (RuntimeData.currentDay < mapConfig.maxDay || RuntimeData.isEndlessMode) return;
    if (playerData.money >= RuntimeData.victoryTarget) {
        RuntimeData.isWin = true; RuntimeData.isEndlessMode = true;
        RuntimeData.currentPhase = GamePhase.GameWin; playerData.loan = 0;
    } else {
        RuntimeData.isGameOver = true; RuntimeData.currentPhase = GamePhase.GameLose;
    }
}
```

**命名规范制定：** 我在团队文档中统一了所有字段命名——体力用Energy不用Stamina，夜市用Market不用NightMarket，客流用Traffic不用CustomerFlow；配置类用Config后缀，运行时数据用RuntimeData后缀，管理器用Manager后缀。

## 4 地图与地块系统实现（牛楚源）

### 4.1 子任务描述

我的任务是让玩家能在校园地图上"走路"。MapManager负责加载地图、算路径、判断能不能走；TileManager负责到达地块后发生什么交互；PlayerMover负责让棋子动起来。这三个系统合在一起就是玩家白天的全部移动体验。

### 4.2 子任务设计

**地图拓扑：邻接表+双向边**

地图本质是一个图结构。我选择用**邻接表**：每个TileConfig保存nextTileIds列表，列出直接连接的地块ID。MVP阶段所有道路双向，如果A连B，B必须连A。

  Shop（商店）×3    |  Event（事件）×5         |  Special（特殊）×2
```

**路径算法：BFS搜索**

```
BFS过程示意（骰子点数=3，从南一门出发）：

  第2步可达: 主图书馆, 百景园

## 5 资源与经济系统实现（邵星岩）

### 5.1 子任务描述

经济系统是游戏的心脏——所有玩法最终都落到"钱"上。我负责四块内容：ResourceManager管玩家口袋里所有资源的进出；EconomyManager管每晚收入结算和贷款利息；CustomerManager管客流分配到各摊位；以及把MarketManager接上资金检查，让建设和升级夜市真正"花钱"。

### 5.2 子任务设计

**ResourceManager——安全第一原则**

资源操作最怕"扣了钱事没办成"。我严格遵循三段式设计：Check（检查够不够）→如果够才Spend/Consume（扣费）→扣完再执行。执行失败Rollback（加回来）。所有操作幂等——多次调用不重复扣费。

**EconomyManager——多层系数链**

收入结算我花最多心思。游戏里有太多因素影响最终收入：天气、卫生、等级、食材、客群……每条系数链对应一个玩家决策维度：

```
有效客流 = 基础客流 × (1 - min(1, competition×0.5/100)) × 等级加成
摊位客流 = 有效客流 × (摊位吸引力/总吸引力) × 偏好倍率
摊位收入 = 摊位客流 × 客单价 × 消费力 × 食材惩罚(不足×0.5)
夜市收入 = Σ摊位收入 × 卫生加成(0.95~1.1) × 4级加成(1+reputation×0.01)
总收入   = Σ夜市收入 × 天气倍率(0.7~1.1)
```

**CustomerManager——客群匹配：** 地块有四类客群比例，摊位有四类偏好倍率。教学区建摊贩（学生偏好1.5），商圈建连锁店（游客偏好1.4），因地制宜获得更高收入。

**事务封装——花钱的"安全气囊"：** 四个核心操作（购买地块/建设摊位/升级摊位/升级夜市）统一模板：

```
bool Transaction(参数) {
    if (!CanXxx(参数, out reason)) return false;      // Step1:检查
    if (!resourceManager.SpendMoney(cost)) return false; // Step2:扣费
    if (!ExecuteXxx(参数)) {                             // Step3:执行
        resourceManager.AddMoney(cost); return false;    // 回滚
    }
    return true;
}
```

### 5.3 子任务实现

**ResourceManager核心：**
```csharp
public bool SpendMoney(int amount) {
    if (playerData.money < amount) return false; // 不足不扣费
    playerData.money -= amount; return true;
}
public bool ConsumeLowFood(int amount) {
    if (playerData.lowFood < amount) return false;
    playerData.lowFood -= amount; return true;
}
public void RestoreEnergy(int amount) {
    playerData.energy = Mathf.Min(playerData.energy + amount, playerData.maxEnergy);
}
```

**贷款利息处理（复利逻辑）：**
```csharp
public void ProcessLoanInterest(int currentDay, int interval, float rate) {
    if (currentDay % interval != 0) return;
    int interest = Mathf.FloorToInt(playerData.loan * rate);
    if (!resourceManager.CheckMoney(interest)) {
        playerData.loan += interest - playerData.money; // 差额滚入本金
        playerData.money = 0;
    } else resourceManager.SpendMoney(interest);
}
```

**数值等级参考：** 所有数值按策划规范的五个量级配置——资金(元)从1~500(很少)到50,000+(很多)，体力上限60(中等)，基础客流50~100(中等档)。

### 5.4 子任务测试

SpendMoney不足时不扣费——这个"不扣费"是关键，如果实现成"扣了但返回false"会导致资金丢失。食材消耗同样验证不足时返回false不消耗。夜晚结算用模拟夜市验证多层系数正确叠加，特别测试了食材不足时收入五折惩罚。

### 5.5 子任务小结

每个系数看似只是一个乘数，但放在一起决定了玩家行为模式。食材惩罚迫使关注供应链，卫生加成让维护有利可图，天气变化要求随机应变。好的经济系统不是"算得准"，而是"让玩家有得选"。

## 6 随机事件与天气系统实现（文智强）

### 6.1 子任务描述

给游戏注入"不确定性"。EventManager决定玩家"中奖"还是"踩坑"；WeatherManager决定今晚晴空万里还是风雨交加；InspectionManager决定夜市卫生会不会被查。三个系统联动让每一局游戏都有不同体验。

### 6.2 子任务设计

**两种事件触发模式：**
- **TriggerEvents（批量触发）**：用于DayStart/NightStart/Inspection等全局时机。遍历事件池筛选符合triggerType的事件，每个按独立概率判定。多个事件可同时触发带来组合效果——早上既触发"社团活动"(+口碑)又触发"物价上涨"(-资金)。
- **PickAndExecuteFromPool（精确抽取）**：用于到达地块等"只抽一个"场景。MapManager传入eventPoolId，从对应池中随机抽一个执行。

**事件池风险收益平衡设计：**

| 事件池 | 数量 | 触发时机 | 风险设计 |
|:-----:|:---:|---------|---------|
| ARRIVE | 9 | 到达地块 | 中低额度为主，概率5%-18% |
| DAY_START | 7 | 每天开始 | 全局效果，含纯文本提示 |
| NIGHT | 8 | 夜晚开始 | 客流倍率±15%~±30% |
| INSPECTION | 5 | 卫生检查 | 含二选一"检查员暗示" |

**二选一事件处理流程：**

```
EventManager.TriggerEvents(OnInspection)
    ↓ 检测到requireChoice==true
    ↓ 不立即执行效果，返回EventRuntimeData
UI弹窗展示两个选项
    ↓
┌───────────────────┬───────────────────────┐
│ 选项A: 给好处费    │ 选项B: 公事公办       │
│ (-500元, 跳过检查)  │ (正常检查流程)        │
└────────┬──────────┘ └──────────┬───────────┘
         ▼                       ▼
  MakeEventChoice(A)       MakeEventChoice(B)
   扣500元+跳过              卫生<70则停业
```
图6-1 二选一事件处理流程图

**WeatherManager权重随机：** 权重设计参考武汉气候——晴天40% > 多云25% > 小雨20% > 炎热10% > 暴风雨5%。

**InspectionManager卫生检查：** 触发概率=5%基础+地块加成+卫生修正(<50:+25%; <70:+10%; ≥70:0%)。通过标准总卫生值≥70，不通过停业2天+罚款1000元。
